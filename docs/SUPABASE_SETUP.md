# Настройка Supabase

Для прототипа нужны только два включённых механизма: **анонимная авторизация** и **Realtime**. Таблицы и миграции не требуются.

## 1. Создание проекта

1. Зарегистрируйтесь на https://supabase.com и создайте проект (регион выбирайте ближе к игрокам).
2. Дождитесь окончания инициализации.

## 2. Анонимная авторизация

1. Откройте **Authentication → Sign In / Providers** (в старом интерфейсе: **Authentication → Providers / Settings**).
2. Найдите **Allow anonymous sign-ins** и включите.
3. Сохраните.

Без этого игра покажет сообщение «В проекте Supabase выключена анонимная авторизация».

### Лимиты анонимных входов

По умолчанию Supabase ограничивает число анонимных входов с одного IP (около 30 в час). На мероприятии все дети могут сидеть в одной Wi-Fi сети, то есть с одного IP, а каждая новая вкладка или перезапуск браузера создаёт нового анонимного пользователя. Перед запуском:

- откройте **Authentication → Rate Limits** и увеличьте лимит анонимных входов (например, до нескольких сотен в час);
- не гоняйте массовые тесты прямо перед мероприятием с той же сети.

## 3. Realtime

1. Откройте **Project Settings → Realtime** (или **Realtime → Settings**).
2. Убедитесь, что Realtime включён.
3. Для прототипа каналы публичные: **Enable Realtime Authorization / private-only channels** должно быть **выключено**. Если есть переключатель **Allow public access**, он должен быть включён.

Игра использует каналы вида `room:ABC123` с Presence и Broadcast. Данные через базу не идут.

## 4. Ключи для frontend

1. Откройте **Project Settings → API** (или **API Keys**).
2. Скопируйте:
   - **Project URL** в `VITE_SUPABASE_URL`;
   - ключ **anon / publishable** в `VITE_SUPABASE_ANON_KEY`.
3. **Никогда** не используйте `service_role` / secret key во frontend и не коммитьте его в репозиторий.

Локально значения лежат в файле `.env` (он в `.gitignore`). Для GitHub Pages они задаются как Actions Variables, см. [DEPLOYMENT.md](DEPLOYMENT.md).

## 5. Проверка

1. `npm run dev`, откройте две вкладки.
2. В первой создайте комнату, во второй подключитесь по коду.
3. Двигайте персонажа в одной вкладке: во второй он должен плавно перемещаться.

Если что-то не работает, откройте консоль браузера (F12) и вкладку Network → WS: там видно соединение с `wss://<проект>.supabase.co/realtime/v1/websocket`.

## Ограничения безопасности прототипа

Текущая модель: «знаешь код комнаты, значит, можешь войти».

| Что хотелось бы | Как сейчас | Как усилить до публичного запуска |
| --- | --- | --- |
| Проверка членства в комнате | Нет | Таблицы `rooms` и `room_members`, вход через RPC-функцию (`join_room(code)`), которая проверяет лимит 4 и статус комнаты |
| Закрытый доступ к каналам | Канал публичный | Приватные каналы Realtime + политики RLS на `realtime.messages` (разрешать только участникам комнаты) |
| Защита от посторонних | Только неочевидность кода (6 символов из 31) | Короткоживущие коды, срок действия комнаты, ограничение попыток, CAPTCHA для анонимного входа |
| Серверная проверка действий | Нет: клиент сам сообщает позицию | Игровые действия (нажатие плиты, голос, подбор предмета) через RPC / Edge Functions, состояние комнаты в базе |
| Лимит 4 игроков | Проверяется клиентами по Presence | Проверка в RPC при вступлении (уникальный индекс / счётчик в `room_members`) |
| Удаление и завершение комнат | Комната исчезает, когда все вышли | Поле `status` (`lobby` / `playing` / `finished`), периодическая очистка (pg_cron или Edge Function) |

Эти шаги не нужны для проверки базового мультиплеера, но обязательны перед открытым запуском. Архитектура уже разделяет сеть и игру (`GameBridge`, `roomService`), поэтому замена реализации не затронет сцены Phaser.
